# Didit Ruby SDK (`sdk-ruby`)

The official Didit server-side library for Ruby: `didit-sdk` on RubyGems.
Status: in development, not released.

## Read first

- `docs/DESIGN.md` is the shared contract of all seven Didit server SDKs (`sdk-python`, `sdk-node`, `sdk-go`, `sdk-java`, `sdk-php`, `sdk-ruby`, `sdk-dotnet`). It is binding: when this code and the design disagree, the code is wrong.
- `openapi/` holds the API contract this SDK is generated from (see DESIGN.md section 3).

## Toolchain

Ruby 3.1 or newer, Bundler, RSpec, WebMock, RuboCop, RBS signatures checked with Steep (Steep needs Ruby 3.3 or newer; the Gemfile installs it only there).

## Commands

```sh
bundle install                    # install the development gems
bundle exec rake generate         # regenerate the generated layer from openapi/ (ruby codegen/generate.rb)
bundle exec rake generate:check   # fail when the committed generated code is stale
bundle exec rake spec             # all unit tests (spec/); live smoke tests are skipped
bundle exec rake codegen:spec     # the generator's and the spec sync's own tests (codegen/spec)
bundle exec rake rubocop          # lint
bundle exec steep check           # type check (Ruby 3.3+)
bundle exec rake build            # build the gem into pkg/ (never publishes)
COVERAGE=1 bundle exec rspec      # fails under 90 % line coverage of the hand-written core
ruby codegen/spec_sync.rb         # download the upstream spec, regenerate, summarise the changes
DIDIT_SANDBOX_API_KEY=... bundle exec rspec --tag live   # live smoke tests against a sandbox application
```

## Layout

- Generated (never edit by hand): `lib/didit/resources.rb`, `lib/didit/resources/`, `lib/didit/types.rb`, `lib/didit/types/`, `sig/didit/resources*`, `sig/didit/types/`, `spec/generated/`.
- Generator: `codegen/generate.rb` and `codegen/lib/didit_codegen/` (reads only `openapi/`); spec sync: `codegen/spec_sync.rb`.
- Hand-written core: `lib/didit.rb`, `lib/didit/client.rb`, `errors.rb`, `model.rb`, `page.rb`, `file_part.rb`, `raw_response.rb`, `resource.rb`, `lib/didit/internal/` (configuration, transport, retries, multipart, logging).
- Webhooks: `lib/didit/webhooks*` (DESIGN.md section 9). Authentication: `lib/didit/authentication*` (DESIGN.md section 10).
- Signatures for everything in `lib/` live in `sig/`, mirroring the paths.
- Tests: `spec/didit/` (core), `spec/webhooks/`, `spec/authentication/`, `spec/contract_spec.rb` (spec operations == SDK methods), `spec/generated/`, `spec/live/`; generator tests in `codegen/spec/`.
- CI: `.github/workflows/ci.yml`; spec sync: `.github/workflows/spec-sync.yml`; release (gated, never run before approval): `.github/workflows/release.yml`.

## Rules

- Generated code is never edited by hand. Change the generator in `codegen/` or `openapi/overlay.json`, then regenerate; CI fails when the committed generated code is stale.
- `openapi/verification.json`, `openapi/account.json` and `openapi/webhook-vectors.json` are upstream copies; never edit them by hand. Only the spec sync workflow updates them.
- Keep the SDKs in sync (HARD RULE). Any public API change in `service-didit-verification` or `service-didit-auth` must reach the OpenAPI documents in mintlify-docs, and from there every server SDK through the spec sync pull request. A change to hand-written core behaviour that DESIGN.md describes (client options, errors, retries, pagination, webhooks, Authentication) is made in all seven SDK repositories, one pull request each, and DESIGN.md is updated in all seven in the same words.
- Feature parity across languages: a capability shipped in one server SDK ships in the other six.
- Never publish a package, push a release tag or make this repository public without Alex's explicit approval; nothing is released before the 2026-11-01 Didit release.
- Unit tests never touch the network. Live smoke tests run only when `DIDIT_SANDBOX_API_KEY` is set.
- Never commit secrets, API keys or real customer data. Fixtures are synthetic.
- `CHANGELOG.md` is generated by release-please from conventional commits; never edit it by hand.
- Public API changes need tests, README updates and a conventional commit type that matches their semver impact.
